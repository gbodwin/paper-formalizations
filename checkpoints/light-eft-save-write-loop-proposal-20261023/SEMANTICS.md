# Conditional exact-byte/ordered-chunk argument and failure boundary

Premise: the original parent owns a fresh ordinary private TextIOWrapper; its write method and the standard JSON encoder implementation are not mutated during a save. The record is the supported ordinary JSON/basic-value graph assembled by the existing authenticated contexts, with the original immutable/no-writer process/source contract. The proposal does not claim arbitrary custom-writer, concurrent monkeypatch, mutable user encoder or interpreter-independent equivalence. Exact active interpreter/default encoder semantics must be reviewed before any future qualification; CPython v3.12.3 primary references are analytical evidence, not attestation of the old or next hosted interpreter.

With indent2 the referenced original json.dump uses a fresh JSONEncoder and its iterencode generator ([primary source](https://raw.githubusercontent.com/python/cpython/v3.12.3/Lib/json/__init__.py)). The proposal supplies the same skipkeys/ensure_ascii/check_circular/allow_nan/indent/separators/default/sort_keys values. It yields the same JSON chunks in the same insertion/traversal order. Binding this stable private writer changes no chunk or write argument. By induction after each returned write, both have submitted the same prefix to the same buffered file implementation. The explicit trailing newline and every subsequent flush/fsync/rename/directory operation are unchanged. Thus successful complete files have the same bytes and digest, with every original saved state committed at the same source callsite. There is no cross-call record/encoding cache or freshness substitution.

For an encoder exception after a prefix, both consume the same generator and have issued the same earlier chunk writes; neither full-buffer-precomputes nor loses a pending chunk batch. For a write failure at a given chunk, both invoke the same underlying write with the same argument and do not add an EINTR retry. The original context-manager close/error behavior and outer fail-stop/retry/lease logic remain. On flush/file-fsync failure no new rename is promoted; on rename/directory-fsync/close failure the original recovery behavior remains. No exception is swallowed, converted to success or moved outside supervision. Asynchronous interruption, allocation-failure timing and unsupported writer mutation cannot be assigned an identical instruction/first-error trace; the requirement retained there is original fail-closed cleanup and exclusion, not a fabricated arbitrary fault-schedule equivalence.

Alternatives considered:

- Cross-state save batching/coalescing would omit independently durable states and fsync pairs, and is rejected.
- Whole-record dumps/join buffering would change partial temp-file/error behavior and memory use, and is rejected here.
- Coalescing output chunks would alter write/failure boundaries and require extra proof/validation, and is deferred.
- IOBase.writelines uses a C loop but the inspected CPython implementation retries EINTR around write ([primary source](https://raw.githubusercontent.com/python/cpython/v3.12.3/Modules/_io/iobase.c)). It is not accepted as preserving the original failure contract.
- Caching the dominant package-selection fragment would require additional typed/order/mutation/failure evidence and serializer surgery; its large measured byte span alone does not justify such a cache.

This bounded candidate preserves per-chunk streaming, no added retry and every durability boundary, but remains UNEXECUTED and conditionally source-argued. Performance, actual error-prefix equivalence and resource fit are not established by this argument. Future failure validation must compare encoder failures and write/flush/fsync/rename/directory failures, sticky error handling and temp/final bytes without weakening any original guard.
