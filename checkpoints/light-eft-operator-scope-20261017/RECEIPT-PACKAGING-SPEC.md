# Static artifact receipt and packaging validation specification

PREPARATION ONLY. This document specifies future checks, not an implemented or exercised validator, approved artifact, or permission to run extraction. Preserve all prior receipts and rejected attempts. No fallback compiler/build is allowed.

## Identity chain and required receipts

1. **Frozen inputs.** Record production `78cb40c7837db049d645d73696f2e0b724ce8a3b`, all nine package revisions and tracked cleanliness, `lake-manifest.json` SHA256, official toolchain version and distribution hash, reviewed mapping implementation commit/hash, source bytes/hashes, ordered imports, root hash and every derived archive key. Require exactly the 3,808 mapped dependencies; bind the unchanged full map SHA256 `7c5150b666457ce16e835cdb2b5044ea8d2a29f005d05a79d5cbaf772af540b5`. A later source change requires a new map/review.
2. **One retrieval receipt per archive.** Unique attempt UUID; source/map/key binding; request method/URL/UTC and monotonic start/end; standard TLS verification result; final URL and redirect chain if any separately allowed; ordered response headers/status; peer-certificate capture result or explicit limitation; full body length/SHA256; storage identity; errors/truncation; outcome. Exclude credentials/cookies/tokens. A cache filename, nonempty body or HTTP 200 alone is insufficient. Require reviewed official-origin authentication, complete expected archive bytes and agreement with any selected candidate. A 403/error body is failure evidence, never an archive. Denied routes stop; no automatic endpoint/identity substitutions. Store failed receipts without overwriting them.
3. **Official extractor distribution.** Bind the official release URL `https://github.com/leanprover/lean4/releases/download/v4.34.0/lean-4.34.0-linux.tar.zst`, successful origin/redirect receipt, complete 580,367,391-byte distribution and reviewed SHA256 `caaa98356098c85dc0fcbbd28e1ec66f39eb6551829972b752ff20e1286b646b`. Independently compare the `leantar` member with the intended executable (candidate 2,692,960 bytes; SHA256 `06d613dffd2a6fd996b095bfd835c2bb720886f9eb7e13ed2adddd7df4507bf3`). Local hashes alone do not prove fresh origin or member identity. Distribution inspection/extraction requires separately authorized handling; none occurs here.
4. **Extraction execution, only after approval.** Unique source/input-bound UUID; reviewed executable and hash; exact argv with no `--delete-corrupted`; stdin bytes/hash; all input archive hashes; fresh staging path and empty-state check; environment allowlist; universal lock identity/ownership; supervisor/child PIDs and process identity, UTC/monotonic times, resource admission, exit status, raw stdout/stderr and child reaping. Keep sequential execution. Verify retained input hashes before and after. Any mutation, ambiguous process state or missing receipt fails closed. Hash-verified read-only/disposable inputs may be designed later, but no such substitute is presumed here.
5. **Complete output inventory.** Account for every extracted path before filtering: type, canonical relative path, bytes/hash, package/module/source hash, all contributing archive hashes and disposition. Reject absolute/traversal paths, links, special files, unclassified outputs and conflicting cross-archive collisions. Identical duplicate contributions must remain visible in provenance. Unknown output cannot silently disappear from evidence. Required cache members missing from a successful archive also fail completeness checks.
6. **Dependency-only bundle.** Only the exact consumer schema `.lake/packages/<pinned-package>/.lake/build/lib/lean/<mapped-module><allowed-suffix>` may enter. Allowed suffixes remain `.olean`, `.olean.server`, `.olean.private`, `.ilean`, `.ir`. Bind every member to its source, producing archive(s), length and SHA256. No project objects, existing project object fallback or unrelated module files. Include complete immutable manifest identity, pins, toolchain, map/provenance review, bundle URL, bytes/SHA256 and deterministic ordering. Verify bundle member set equals manifest member set plus the one manifest; validate every member before installing anything. Destination overwrite/symlink checks must fail closed.

## Packaging disposition

| Extracted type | Disposition |
| --- | --- |
| Five allowed object suffixes above | Eligible for bundle only after complete source/archive/path/hash validation. |
| `.trace`, `.olean.hash`, `.olean.server.hash`, `.olean.private.hash`, `.ilean.hash`, `.ir.hash` | Retain in staging and complete evidence inventory; exclude from installable bundle. Their internal hashes are not substitutes for external SHA256 provenance. |
| `.ir.sig`, `.ir.sig.hash` | Retain and inventory; exclude under current consumer contract. If necessary for planned loading, stop for reviewed contract revision rather than silently dropping a required dependency or expanding the allowlist. |
| `.c`, `.c.hash` | Retain and inventory; exclude from bundle; no native compilation/linking. |
| `.extra` | Inventory and quarantine pending explicit contents review; exclude from bundle. |
| Anything else | Refuse packaging, preserve raw output and diagnosis. |

## Required future validation cases

Positive: exact pinned map + authenticated complete archives + reviewed extractor + complete inventory + valid dependency-only bundle. Negative: wrong/partial/duplicated map; source or pin drift; HTTP 403/redirect outside reviewed route; truncated archive; same filename/different bytes; wrong distribution or extractor member; input mutation; deletion flag; missing lock/PID/source/exit/reaping receipt; overlapping invocation; unsafe output path/link; conflicting output; absent required member; `.trace`/`.c`/`.ir.sig` slipping into object bundle; project/unmapped object; bundle/manifest/member hash mismatch; destination collision. Each must produce an explicit rejection without executing a fallback or altering retained evidence.

These cases are a specification, not claims of passing tests. Execution approval must separately resolve official access, effective resource accounting, native extractor review and the final artifact-bearing harness. The current workflow still guards the accepted preparation harness; no installation/dispatch is authorized.
