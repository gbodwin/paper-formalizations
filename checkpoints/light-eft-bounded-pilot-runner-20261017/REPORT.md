## Pre-exec and process containment

The unchanged universal lock is opened without creation/replacement and acquired nonblocking. Its device/inode/fd is recorded. After streaming input hashes, admission requires visible headroom and system MemAvailable each >=2 GiB and disk >2 GiB, no competing Lean/Lake/checker/extractor and no preexisting children. The accounting label is explicitly `PARTIAL_VISIBLE_ANCESTORS`; hidden ancestor limits remain unknown.

A minimal isolated Python launcher starts in a new session and inherits the held lock descriptor. It sets **soft=hard** RLIMIT_AS=1,610,612,736 bytes, RLIMIT_CPU=60 seconds, RLIMIT_FSIZE=16,777,216 bytes and RLIMIT_CORE=0, then reads them back. It sends its PID/PPID/session/group, limits and lock identity through an inherited pipe and blocks awaiting approval. The supervisor independently reads kernel limits with `prlimit`, verifies process/session identity and the inherited lock descriptor, persists the handshake, then sends the one-byte go-ahead. Only then does the launcher `execve` the exact pinned payload in the same PID. Limit setup/readback failure or missing approval never executes the payload. This is process setup, not a Lean runtime shim.

Monitoring targets a 250 ms interval (inspection work adds latency) and records process identity, sampled RSS/VM, visible parent and self-group memory limit/current, and OOM counters. Reads use no-follow descriptors with cgroupfs magic and mount-ID/inode checks; namespace, membership, mount layout, limits and file identities must remain stable. Any unreadable/changed accounting identity, headroom <512 MiB, changed OOM count, lost child/lock identity, observed unexpected descendant or 90-second child wall deadline fails. The timeout terminates the child, never the supervisor. Child exit status and maximum RSS come from the runner's exclusive direct-child `wait4`; it sets `Popen.returncode` before calling lifecycle cleanup, so cleanup's `poll()` cannot steal that reap. `wait4` maximum RSS covers the launcher and payload process lifetime. VM peaks are explicitly **sampled**, not continuous maxima.

Subreaping, group/descendant termination, adopted-child reaping, sticky cleanup errors, lock retention through recovery and the kernel ECHILD release proof reuse the unchanged `LightEFTProcessLifecycle.py`. Supervisor signal handlers and a fail-stop finalization barrier retain exclusion on unknown cleanup outcomes. Receipt persistence is atomic and fsynced. The lock is released only after direct-child reap, descendant cleanup/ECHILD, post-input checks and final receipt. If direct-child ownership unexpectedly becomes ambiguous, cleanup fails closed under the lock.

**Observation limitation:** the runner fails on every descendant it observes, including detached/adopted children found during cleanup. Periodic `/proc` sampling cannot establish that no child spawned and self-reaped wholly between samples. No syscall tracing or fork-prevention security policy was added. Independent implementation review must assess this limitation against the requested descendant condition before authorizing the pilot; this report does not claim a universal no-fork guarantee. Per-process caps and visible monitoring likewise cannot guarantee safety against unseen ancestor limits or external concurrent memory use.
